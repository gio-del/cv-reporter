# Job Listing freshness is a live, on-demand re-fetch, not a cached copy

A Job Listing's source URL liveness (issue #59, "Job Description link-rot / staleness check") is checked by re-fetching the URL on explicit user action and persisting only a classified status (`live`/`unreachable`/`unknown`) plus a checked-at timestamp — never a cached copy of the response, and never on a background schedule. This is the deliberate opposite of ADR-0013's Company Logo handling: ADR-0013 downloads and keeps a stable local copy because the *asset itself* is worth preserving against link rot, whereas here the Job Description text is already captured as Master Data at save time (see ADR-0008) — there is nothing else worth caching, only the current liveness of the *original* posting, which by definition has to be checked live to mean anything. Kept as an independent module (`backend/internal/freshness`) sharing only the general-purpose injectable-`HTTPDoer` pattern already used by `atsboard` and the Company Logo download, so a bug in one can never affect the other. Considered and rejected: reusing/extending ADR-0013's logo-download pipeline (conflates two unrelated concerns — an asset worth keeping vs. a live check that must never be "cached" without becoming stale itself); adding a background poller to re-check all tracked Job Listings periodically (this repo has no periodic-job infrastructure, and building one is out of proportion to a single on-demand action — explicitly deferred per the PRD).
