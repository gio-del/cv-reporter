# The API contract is checked by golden response fixtures, not generated types

`frontend/src/api/types.ts` is a hand-maintained copy of what the Go handlers put on the wire, and nothing checked the two agreed: by the time issue #99 was audited, `Application.statusHistory`, `GenerationRecord.groundedness`/`language`, `SelectionResult.language` and every record's `schemaVersion` were sent but undeclared, empty Snippet/Entry tags, Static Sections and stats lists arrived as `null` where the frontend declares arrays, `POST /api/ats/tracked-boards` answered without the `newCount` its declared type promised, and `GenerationRecord.usage` carried an `omitempty` a struct value never honours. None of it failed either build.

The contract is now checked from both sides of one artifact. `backend/internal/api/contract_test.go` drives every JSON-returning route through its real handler (the same `httptest` router, fake `tracking.Client` and fake ATS doer the handler tests already use) and compares each normalized response — sorted keys, one fixed timestamp, the Render output directory stamp, Note ids, record version tokens (hashes of file bytes that embed those timestamps) and clock-derived numbers fixed — with a golden JSON file under `frontend/src/api/contract/fixtures/`. A normal `go test` only verifies; `UPDATE_CONTRACT_FIXTURES=1 go test ./internal/api -run TestContract` rewrites. `frontend/src/api/contract/contract.ts` imports each fixture as a JSON module type and asserts it against the declared type with `Contract<Fixture, Declared, Label, Mode, Exempt>` (`check.ts`), which `tsc -b` evaluates: truth flows from the handlers to the fixtures to the type checker, and neither side is generated from the other.

Plain assignment was not enough, because excess-property checks never apply to imported values, so a field the backend sends and the frontend never declared would pass. `Contract` walks the fixture recursively and reports, by route and JSON path, any key sent but undeclared, any required key not sent, any value of the wrong kind or an undeclared `null`. A `populated` fixture must also send every optional key somewhere (so the frontend declares what can arrive), a `sparse` one none (so a field the backend always sends is declared required); a path the scenario cannot reach is exempted from that extra check only, with its reason next to it. `check.expectations.ts` holds `@ts-expect-error` cases for each drift class, so a check that stopped catching one fails the build. Coverage is an explicit list: `TestContractRoutesAllCovered` parses `router.go` and fails on a route with neither a fixture nor a reasoned exemption, and `TestContractFixtureFilesMatchRegistry` fails on a stale fixture file or one `contract.ts` never asserts.

Considered and rejected:

- **Generating the TypeScript types from the Go structs** (or from OpenAPI/JSON Schema). Several wire shapes are unexported API-layer DTOs — `tagLintReport`, `snippetWithUsage`, `jobListingSummary`, `trackedBoardWithNewCount` — so generating from domain structs would be wrong for exactly those routes; it would add the repo's first generated-artifact workflow; and it would discard the explanatory comments `types.ts` relies on.
- **A runtime schema validator** declaring schemas once for both types and checks. It catches more, but means rewriting `types.ts` into schema declarations and shipping a runtime dependency for a development-time guarantee.
- **Asserting fixtures in a JS test runner.** `tsc -b` already runs in CI and needs no runner, so the check does not depend on Vitest (ADR-0019).

Consequences: any PR that changes a response shape regenerates fixtures and shows the change as a JSON diff, and must update `types.ts` in the same PR. Only response bodies are covered; request bodies, paths, status codes and error bodies are not. String-literal unions are compared as strings, since JSON module imports widen literal values.
