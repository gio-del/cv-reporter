# The tailor-cv skill runs the app's quality checks through one Go implementation, via a CLI

ADR-0016 closed one silent divergence between the skill's render path and the container's (the typst version/font pin) with a shared file and a non-blocking preflight script. A larger one remained: an app-run Generation gets automated checks — groundedness of every rewritten bullet (guarding Rewrite's no-invented-facts rule, see ADR-0002/ADR-0010), ATS-parsability of the rendered PDF's text layer, a mechanical page count, and a normalized target language stamped into the document — while a skill-run Generation got none of them, so the same Tailored CV was scrutinized differently depending on the entry point (issue #104). Check *parity* between the two paths is now achieved by both calling one Go implementation: `backend/internal/generation` exposes one thin facade per check point (`CheckSelectionGroundedness` for Text Review, `CheckRenderedCV` for Visual Review) over the existing unexported check functions, and a small CLI, `backend/cmd/cvcheck` (subcommands `groundedness` and `pdf`), calls those facades; the skill shells out to it through `plugins/cv-reporter-skills/skills/tailor-cv/scripts/quality-check.sh`, which builds the binary from the checkout's own `backend/` source so it can't go stale. The CLI takes file paths to artifacts under `output/<slug>/` (including a new `selection.json` holding the skill's source→rewritten bullet pairs as a `SelectionResult`, which it previously discarded at Assemble), prints human-readable text or, with `--json`, the same result types the API returns, and exits 0 (clean), 1 (flagged) or 2 (couldn't run) — none of which the skill treats as fatal, keeping every check a signal inside an existing Human-in-the-Loop checkpoint rather than a new gate.

Two alternatives were rejected. **Having the skill call the running container's API** would make `docker-compose up` a precondition for the two skill modes SKILL.md promises work without a backend, reversing a stated contract for no gain: the checks are pure, offline computations (token overlap and a `pdftotext` subprocess — no Claude call, no server-side state), and HTTP would only add a connection-refused failure mode in front of them. **Describing the checks in prose for the model to perform** is the worst option despite looking cheapest: a model grading its own Rewrite for groundedness is exactly the unreliable judgment the deterministic check exists to replace, and a prose restatement would start drifting from the Go implementation the moment either changed — two implementations disagreeing about one input is a worse form of the divergence being fixed. Usage/cost recording stays out of scope on principle: it measures the backend's own Claude API calls, and a skill run makes none, so there is no honest figure to record. Language detection stays with the model (the skill is Claude), but normalization to the supported set uses the app's `NormalizeLanguage` rule, surfaced by the CLI.
