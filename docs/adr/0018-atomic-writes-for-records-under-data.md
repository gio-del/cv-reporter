# Records under `data/` are written atomically, derived artifacts are not

Every write under the data directory — Master Data Entries, Cover Letter Snippets, the profile, Job Listings, Applications, the usage log, the ATS tracked-boards and seen-listings state, a downloaded Company Logo — goes through one helper (`backend/internal/atomicfile`) that writes a temp file in the *same* directory and renames it over the target; writes under `output/` stay on the plain whole-file write. ADR-0003 and ADR-0008 make these flat files the database: there is no second copy, and a plain write truncates the target before refilling it, so a process killed mid-write (or a full disk) destroys a record rather than leaving the previous version — with an Application that means its entire Status history and every Generation record. The scope line is the existing source-versus-derived split (ADR-0012, CLAUDE.md's "`output/` is derived, not Master Data"): losing a rendered PDF means re-running a Render, so future write paths are in or out without a per-file judgment call. Mechanism notes: the temp file must live in the target's directory because rename is atomic only within a filesystem and `data/` is a bind-mounted volume in the container; temp names are dot-prefixed and never end in `.md`/`.yaml`/`.json`, because both list paths enumerate records by the `.md` suffix and fail the *whole* collection on one unparseable file, so a temp file stranded by a crash must be invisible to them; the requested permission mode is set explicitly, since temp files are created owner-only while today's records are world-readable for the `tailor-cv` skill and the user's editor; and the temp file is flushed but its directory is not synced — the failure modes this addresses (process killed, container stopped, disk full) are covered by flush-then-rename, whereas directory syncing buys durability against sudden power loss that a personal single-user tool does not need. Considered and rejected: an unexported copy of the helper in each package (two copies of the exact code introduced to stop inconsistent writes); a filesystem abstraction to inject write failures (a seam spread across every store for one test — a read-only directory forces the failure with the standard library alone); and file locking, which addresses two writers racing, a different failure needing a different mechanism.
